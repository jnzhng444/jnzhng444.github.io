Reviewed [Arquitectura de Computadores II](https://github.com/Fabbbri/fgonzalez_a2_2026_s2) and its [Ray Tracing implementation](https://github.com/Fabbbri/fgonzalez_a2_2026_s2/tree/master/ray%20tracing) at commit `b9abe7f06d8cd5436c6be73d74fc66d1f97f3291`, branch `master`. Evidence: root README, `ray tracing/README.md`, `ray tracing/docs/diseno.md`, and `src/execution/fine.cpp`, `coarse.cpp`, `parallel.cpp`. The user explicitly identifies Ray Tracing as their contribution among four team workloads; the other workloads are context only.

The CPU C++17 renderer uses sampled, bouncing paths through matte, metallic and glass spheres, shares scene/camera/tile partition across models, and presents the completed image with SDL2. Five models are implemented: sequential baseline; cooperative Fine-Grained on **one real OS thread**, taking up to K complete pixels per turn; Coarse-Grained with modeled blocking/resumption and optional bounded workers; SMT workers assigned according to logical topology; CMP workers on distinct physical cores. Selecting the SMT policy alone does not enable hardware SMT.

The browser's animated rays, tile blocks and five selectable maps are original explanatory graphics, not a renderer port, hardware trace or benchmark. Block widths and animation periods do not claim measured speedups. Existing benchmark and perf infrastructure supports runtime, speedup, efficiency, scalability and Amdahl analysis, but no numeric performance result was added to the portfolio or independently reproduced.

## Demonstration boundaries

- Hero: original layered SVG chip, CSS depth, moving circuit signals and moderate scroll parallax. It represents engineering interests, not processor authorship or a trace from the real compiler. A brief typographic mask reveal introduces 欢迎 without imitating stroke order.
- Compiler: hand-authored pseudocode → syntax tree → semantic checks → IR → DCE/copy propagation → generic RISC-like pseudocode. Explicitly not actual Craft syntax, Craft21 instructions, a real compiler invocation, or benchmark output. The same input-plus-one observable behavior is preserved. The project has more optimization passes than this tiny teaching example demonstrates. In the redesign, blocks change labels, the independent input and unused constant exchange positions, and the dead assignment disappears. A desktop scroll sequence and manual buttons select the same six stages; no source execution is implied.
- Scheduler: actual local calculation, with A `(C=2, T=D=5)` and B `(C=4, T=D=7)`, synchronous release at zero; independent periodic jobs on one preemptive CPU; integer ticks; zero overhead. Fixed shorter-period priorities for RMS, nearest absolute deadline for EDF. Ties: earlier release, then input order. Late jobs remain queued; completion at a deadline is on time. One 35-unit hyperperiod, checked at the right endpoint. RMS misses B's deadline at 7; EDF meets every deadline. Browser model intentionally omits calibration, communication, sporadic releases and heterogeneous allocation.
- Garage: original fictional track, synthetic fixed telemetry and decorative lap marker. Explicitly illustrative; no real race or project performance measurements.
- New system overview: Craft source → optimizing compiler → Craft21 code → five-stage pipeline, with a simplified L1/L2/main-memory hierarchy. It shows integration context, not a live execution or cache simulation. The compiler's illustrative stages now play automatically while visible; a manual choice stops playback.
- ChaCha20: a conceptual 16-word state (constants, key words, counter, nonce), add/XOR/rotate mixing and keystream XOR. No encryption is performed in the page, and no key material or actual cipher output is shown.
- MPointer: two references to an allocation, followed by a conceptual zero-reference state after release. No live memory trace or cycle-collection capability is claimed.
- Signals/control: illustrative signal/spectrum/reconstruction curves and a separate PID feedback loop. No measured signal, compression ratio or controller performance is presented.
- Architecture: Pico W provides operand A over SPI, separate serial input provides B to the FPGA ALU, and outputs include LEDs/seven-segment displays/PWM. A separate five-stage RISC-V simulator diagram describes educational software, not an FPGA RISC-V CPU or full ISA implementation.
